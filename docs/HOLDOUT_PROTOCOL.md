# 保留段使用协议

本协议规定保留段的资格、登记、执行、判定与披露。执行器为 `scripts/holdout_eval.py`,票据格式见 `tasks/holdout_tickets/README.md`,测试见 `tests/test_holdout.py`。

截至本文档提交时,**保留段从未被正式使用**,台账中也没有任何候选具备资格(见第 2 节)。本协议与执行器只建不跑。

## 1. 定义

| 项目 | 取值 |
|---|---|
| 保留段 | 合同 `holdout.cutoff`(2024-09-01)起至库内数据末尾 |
| 当前长度 | 497 个交易日,2024-09-02 → 2026-09-18(按 sh.000001 交易日历计) |
| 样本内 | 2015-01-05 → 2024-08-30,2351 个交易日 |
| 数据层约束 | `loader.load_panel` / `loader.index_series` 默认不返回 cutoff 及之后的数据;仅 `unlock_holdout=True` 时返回,且每次在 `meta.holdout_unlocked_log` 追加一条带 UTC 时间的记录 |

保留段长度由对 `index_daily` 的一次只读日期计数得到,只读取了日期列,未读取任何价格或收益字段。

## 2. 原则

1. **一次性。** 以同一 cutoff 为界,保留段只正式使用一次。第一张执行完成的票据即消耗该段,此后的票据一律拒绝。多个候选须在同一张票据中同时申报、一次评估。
2. **资格。** 只有样本内全部门槛通过的候选才能进入票据。台账条目须同时满足以下条件:
   - `verdict = pass`,且 `gates.overall_pass = true`;
   - 泄漏检测与零假设校准均通过;
   - 运行期间没有出处漂移;
   - `git_commit` 不带 `-dirty`。

   截至 BATCH02b,台账共 63 条记录:31 条 fail,32 条 draft,没有 pass。因此当前没有合格候选。
3. **先登记,后使用。** 票据须先提交进 git。执行器只接受已在 HEAD 中、与已提交版本一致、且工作区干净时的票据。
4. **两值标签。** 裁定标签只有 `holdout_consistent` 与 `holdout_inconsistent` 两种,不设"接近""边缘"等中间档。
5. **一致不等于证明有效。** 在当前保留段长度下,一个零技能、纯凭运气越过样本内门槛的策略,被判"一致"的概率约为 0.28(第 6 节)。标签只说明保留段没有明显否定样本内结论,不构成有效性证明。

## 3. 票据

票据文件为 `tasks/holdout_tickets/<ticket_id>.yaml`,须事前写定以下内容:

| 字段 | 内容 | 核对方式 |
|---|---|---|
| `candidates[].factor_name` / `params` | 因子名与规格参数 | 与 `pipeline.discover_specs(include_optional=True)` 解析出的 spec 逐项相等 |
| `candidates[].factor_module_sha` | 因子模块源码 sha(`registry.factor_code_sha`) | 与当前加载的模块、台账 `code_sha` 三方一致 |
| `candidates[].in_sample` | 台账条目 id、平静期超额夏普、平静期天数 | 与台账 `sr_calm` 及证据包中的平静期天数一致 |
| `code.git_commit` | 样本内运行所用提交 | 须为 HEAD 或其祖先;二者之间评估相关路径不得有改动;须与台账 `git_commit` 指向同一提交 |
| `code.contract_sha256` | `contracts/ashare.yaml` 的 sha256 | 与当前合同文件一致;票据 cutoff 与合同一致 |
| `evaluation` | 预热长度、多头比例、基准、区间水平、衰减检验水平、分段 | 写定后不得修改 |

评估相关路径为 `ashare_forge/`、`contracts/`、`scripts/holdout_eval.py`、`requirements.txt`。执行器本身也在其中,因此判定规则的实现不能在看过样本内结果之后再改。

票据中的每一个字段都必须是执行器认识的字段。字段名拼错时,该字段会静默取缺省值,所以出现未知字段一律拒绝。

## 4. 执行器

执行器有两种模式,必须显式选择其一:

| 模式 | 行为 |
|---|---|
| `--dry-run` | 只做全部检查。以 SQLite 只读 URI(`mode=ro`)打开数据库,任何写入都会被 SQLite 本身拒绝;不解锁,不写库,不写文件 |
| `--confirm <ticket_id>` | 真实执行。`--confirm` 的值须与票据 `ticket_id` 一致 |

两个都不给时拒绝运行,以防漏写 `--dry-run` 而误把保留段消耗掉。

检查项如下,dry-run 与真实执行共用。任一项不通过即拒绝,且不解锁:

| 检查 | 内容 |
|---|---|
| `ticket_parse` | 格式、字段、ticket_id 与文件名一致、日期与分段合法(分段不得早于 cutoff) |
| `ticket_location` | 票据直接位于 `tasks/holdout_tickets/` |
| `ticket_committed` | 票据已在 HEAD 中,且与已提交版本一致;仅暂存未提交同样拒绝 |
| `worktree_clean` | `git status --porcelain` 为空,含未跟踪文件 |
| `code_commit` | 见第 3 节 |
| `contract` | cutoff 与合同 sha256 |
| `candidates` | spec 可唯一解析,模块 sha 与参数一致 |
| `in_sample` | 第 2 节第 2 条的资格条件;票据数值与台账一致;基准一致;样本内末日早于 cutoff |
| `single_use` | 本票据未用过;保留段未被消耗;未完成的使用须以 `supersedes` 接续(第 7 节);结果文件不存在 |
| `prior_unlocks` | 信息项:列出 `meta.holdout_unlocked_log` 中的既往解锁记录 |
| `warmup` | 预热充分性:只用 cutoff 之前的数据,分别以 W 与 2W 个交易日预热构造因子,cutoff 前最后一个交易日的因子值须逐项一致,且在池股票的覆盖率不低于票据申报值 |

真实执行的顺序固定:

1. **锁定出处。** 进程启动时、任何数据加载之前,记录以下信息:HEAD、工作区状态指纹、合同 sha256、执行器 sha256、票据 sha256、各候选因子模块 sha,以及 Python / numpy / pandas 版本。
2. **完成全部检查。**
3. **登记 started。** 在同一个写事务(`BEGIN IMMEDIATE`)里复核一次性条件,再插入 `holdout_uses` 一行,状态为 `started`。这样即使两个进程同时通过检查,后登记者也会在这一步被拒,且不会解锁。
4. **写起始标记。** 在 `meta.holdout_unlocked_log` 写入 `{"func": "holdout_eval", "phase": "begin", "ticket_id": ...}`。
5. **解锁加载。** 以 `unlock_holdout=True` 加载 [预热起点, 数据末尾]。
6. **同口径回测与评估。** 回测、切出保留段统计量、计算标签与零假设概率。
7. **比对出处。** 重新计算第 1 步的各项并比对。任一项变化即判为出处漂移:不出标签(`label` 为空,`status = invalid_provenance_drift`),保留段仍按已消耗处理。
8. **写结果。** 写结果文件 `tasks/holdout_tickets/<ticket_id>.result.json`,将 `holdout_uses` 置为 `completed`,并在 meta 写结束标记。结果文件须原样提交入库。

退出码:

| 退出码 | 含义 |
|---|---|
| 0 | 检查全过(dry-run),或执行完成 |
| 2 | 拒绝;此时未解锁,也未写 `holdout_uses` |
| 3 | 已登记 started 之后出错;保留段按已消耗处理 |

## 5. 评估口径

**加载窗。** 加载窗为 [cutoff 前第 W 个交易日, 数据末尾],W 缺省为 250。预热段只用于构造因子和形成持仓初态,其收益不计入任何保留段统计量。

**同口径。** 面板、可交易面具、退市清算、交易成本、基准时段(开盘→次日开盘)与 `backtest.run_backtest` 均与流水线相同。`pipeline.load_context` 不接受解锁参数,执行器因此复刻了一份 `build_context`。二者在 cutoff 之前的窗口上逐表相等,由 `test_context_parity_with_pipeline` 保证。

**观测。** 只计收益区间完全落在保留段内的观测:

- 组合第 d 行对应 d 日开盘→次日开盘,只计 d ≥ cutoff 的行;面板末行因次日开盘不可得而剔除。
- IC 按收益区间对齐:t 日因子对应 t+1→t+2 开盘收益,因此 cutoff 前最后一个交易日的 IC 计入保留段。
- 跨界区间(末个样本内交易日开盘 → 首个保留段交易日开盘)两侧都不计。

**主统计量。** 主统计量为保留段超额夏普:相对中证500,开盘→次日开盘,年化因子 243。合同的四段危机窗口均在 2024-02-08 之前,因此保留段全段属于平静期,与样本内的平静期超额夏普直接对照。

## 6. 判定规则与零假设概率

### 标准误

年化夏普估计 Ŝ(日度为 s = Ŝ/√243)在 n 个观测上的标准误,与 `gates.psr` 的分母同式:

SE(Ŝ) = √243 · √[(1 − γ₃·s + (γ₄ − 1)/4 · s²) / (n − 1)]

其中 γ₃ 为偏度,γ₄ 为原始峰度(正态分布时为 3)。真实夏普为 0 时,SE₀(n) = √(243/(n − 1)),与 γ₃、γ₄ 无关。

### 判定

记 S_is 为样本内平静期超额夏普,n_is 为其天数,n_h 为保留段天数,α 为票据申报的衰减检验水平(缺省 0.10)。

τ = max(0, S_is − z₁₋α · √(SE_is² + SE_h,ref²))

其中 SE_is 与 SE_h,ref 都在 S_is 处按正态独立同分布取值,分别对应 n_is 与 n_h。

**holdout_consistent ⇔ Ŝ_h > τ**(严格大于)。保留段夏普不可得时,判 `holdout_inconsistent`。

这条规则的含义是:

- 保留段夏普须为正;
- 相对样本内估计的衰减,在单侧 α 水平上不显著。

τ 只依赖 S_is、n_is、n_h 与 α,不依赖任何保留段收益,因此是事前可算的门限。判定不使用偏度与峰度,原因有二:

- 台账没有记录样本内的偏度与峰度,无法核验;
- 在所涉夏普量级下,它们对标准误的影响只在几个百分点以内。

### 报告内容

结果文件中报告以下各项。区间水平由票据申报,缺省 90%。

| 类别 | 内容 |
|---|---|
| 超额夏普 | 点估计、观测标准误(含偏度峰度修正)与 90% 区间 |
| 衰减 d = Ŝ_h − S_is | 点估计、标准误与 90% 区间 |
| 其他收益指标 | 超额年化、净收益夏普、超额最大回撤 |
| IC | 均值及其 90% 区间,ICIR |
| 交易特征 | 换手、持仓数、年化成本 |
| 分段与敏感性 | 见第 9 节 |

### 零假设下被判一致的概率

以正态近似计算以下三个量:

- **给定观测样本内值:** P₀|is = 1 − Φ(τ / SE₀(n_h))。
- **零技能且被事后挑中:** 样本内夏普估计服从 N(0, SE₀(n_is)²) 截断于入选线 g 以上。对每个入选值,按其 τ 计算 P₀,再按截断正态密度积分。
  - 入选线 g 取以下三者中的最大者:合同绝对线(平静期超额夏普 ≥ 0.8)、PSR ≥ 0.9 的隐含线、DSR ≥ 0.95 的隐含线。DSR 线按台账记录的试验数 n_trials 计算。
  - 同时报告仅按合同绝对线入选时的值。
  - 该积分与蒙特卡洛模拟的一致性由 `test_null_probability_matches_monte_carlo` 保证。
- **判别力:** 若真实夏普等于 S_is,被判一致的概率为 P₁ = 1 − Φ((τ − S_is) / SE_h,ref)。

多个候选时,另报"至少一个被判一致"的零假设概率 1 − Π(1 − P₀,i)。候选之间正相关时,该值为上界。

### 数值示例

以下数值由执行器的函数计算,设定为 n_is = 1990、n_h = 497、α = 0.10、n_trials = 38,与 BATCH02b 的平静期天数、当前保留段长度及当时的试验数相同。

- SE₀(n_is) = 0.350,SE₀(n_h) = 0.700,衰减容许幅度约 1.00。
- 入选线:合同线 0.80,PSR 线 0.45,DSR 线 1.33,有效线取 1.33。

| S_is | τ | P(一致 \| 真实 0) | P(一致 \| 真实 = S_is) | P(一致 \| 真实 = S_is/2) |
|---|---|---|---|---|
| 0.80 | 0.000 | 0.500 | 0.873 | 0.716 |
| 1.00 | 0.000 | 0.500 | 0.923 | 0.762 |
| 1.13 | 0.126 | 0.429 | 0.924 | 0.735 |
| 1.30 | 0.296 | 0.336 | 0.924 | 0.694 |
| 1.50 | 0.495 | 0.240 | 0.924 | 0.642 |
| 2.00 | 0.993 | 0.078 | 0.924 | 0.504 |

一个零技能、在样本内凭运气越过入选线的策略,在保留段被判一致的概率如下:

- 按有效线(1.33)入选:0.280;
- 仅按合同线(0.80)入选:0.489。

读法:497 个交易日的年化夏普标准误约为 0.70,这一长度能识别大幅衰减,但不足以确认有效性。若候选的真实夏普等于样本内估计,被判一致的概率约 0.92;若为零技能,约 0.28。二者之比约 3.3,是一个中等强度的证据。因此标签必须与上述概率一并报告,不得单独引用。

## 7. 中止与接续

执行在登记 started 之后出错时,`holdout_uses` 置为 `aborted`,并记录错误。因为数据可能已被加载,**保留段视为已被触及**。

- 未完成的使用(started / aborted)会阻止后续票据,直至有新票据以 `supersedes: <ticket_id>` 显式接续。
- 接续票据的结果中会列出被接续的使用。
- 已经 `completed` 的使用不可接续。

## 8. 消耗之后

一经消耗,[cutoff, 当时数据末尾] 即成为事实上的样本内。此后任何新候选都需要新的样本外窗口,即消耗时点之后新同步的数据,称为前向保留段。前向保留段须同时满足两个条件:

- 修改合同 cutoff(合同版本递增);
- 执行器按新 cutoff 登记使用。

执行器目前按 cutoff 区分使用记录,已能支持这一做法,但合同变更流程尚未书面化。

## 9. 政策行情的处理

2024-09-24 起的政策驱动行情**不剔除**。标签基于保留段全段,同时按事前写定的分段披露(公开事件粗标,做法同合同危机窗口):

| 分段 | 起止 |
|---|---|
| `pre_policy` | 2024-09-01 → 2024-09-23 |
| `policy_rally` | 2024-09-24 → 2024-10-08 |
| `post_rally` | 2024-10-09 → 数据末尾 |

- 每段报告天数、累计超额、超额年化与 IC 均值;不足 60 个交易日的段不报夏普。
- 另报剔除 `policy_rally` 后的超额夏普,作为敏感性披露,不进入标签。
- 分段只能划分保留段,起点不得早于 cutoff。

## 11. 已知局限

1. **拦截只在加载层。** 直接用 SQL 读取 `daily` / `index_daily` 可以绕过 loader;任何 Python 调用方也可以自行传入 `unlock_holdout=True`。现有缓解手段都属于留痕与审计,不构成技术上的不可能:
   - `meta` 解锁日志:执行器另写 begin/end 标记,使日志中的解锁条目可归属到票据;
   - 代码审查:检索 `unlock_holdout` 与直接 SQL;
   - 票据先提交:登记先于使用,可由 git 历史核验。
2. **标准误按独立同分布计算。** 未计入日收益的序列相关。截面组合的日超额自相关通常较弱,但未单独检验。
3. **入选线只刻画平静期超额夏普的约束。** 危机层、零校准、持仓数等门槛不能表示为 S_is 的函数,未纳入积分。实际入选更严,对应的零假设"一致"概率也可能更低,报告值因而偏保守。
4. **部分运行参数不在台账出处中。** `top_pct`、回测起止日期没有写入流水线的出处记录,只能依票据申报,与 CLI 缺省值(0.1)对照。
5. **因子模块 sha 按模块计算。** 因子所依赖的其他模块的改动,由 `code_commit` 对 `ashare_forge/` 的 git 差异检查覆盖,而不由模块 sha 覆盖。
6. **基准不含分红。** 基准为中证500 价格指数,与样本内口径相同,超额中含约一个指数股息率。
7. **保留段不是市场状态的随机样本。** 它只有约两年,且包含一段政策驱动行情。结论的外推范围相应受限。
